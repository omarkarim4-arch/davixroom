# DavixRoom engineering handbook

Rules for anyone — human or agent — working in this repository. Everything above
this heading is regenerated by `next dev`; everything below it is hand-written
and permanent. Keep new guidance below the marker.

## What the product is for

**DavixRoom's core function is live software review through secure screen
sharing.** A vendor shows working software to a client, in real time, and the
client responds to what they are shown.

Everything else — organizations, projects, invitations, feedback, approvals,
recordings, AI summaries, and eventually remote control — exists to support that
one workflow. The ownership hierarchy says the same thing in structure:

```
Organization → Team Members → Projects → Client Invitations → Review Sessions
```

The last node is the point; the others are the shortest path to it.

When an architectural decision is genuinely open, optimise for the live review
experience, not for generality. Concretely, this means: prefer the change that
shortens time-to-first-review-session; do not build generic collaboration
surface (team consoles, settings screens, org admin) unless a review workflow
needs it; and treat a feature that cannot be traced back to a review as
suspicious until somebody explains the connection.

## How work is sequenced

The project moves in numbered stages (see the roadmap in `README.md`). The rule
is: **propose, wait for approval, implement, verify, commit.** One stage at a
time.

Do not start the next stage because the current one finished early, and do not
widen a stage's scope because adjacent code looks improvable. If you find a real
problem outside the approved scope, say so and keep going — narrowing or
widening the work is the maintainer's call, not yours.

When a phase declares part of the system protected — as the design phase did
with the backend — treat that boundary as absolute. Consume the existing
contracts exactly as they are rather than adjusting them to suit new code.

## Invariants you must not "simplify"

Several things in this codebase look like oversights and are not. Each one is
load-bearing, and each has a comment saying so. Read the comment before you
change the line.

- **Queries deliberately omit tenant filters.** Row level security decides what
  the database hands over. Adding a `where org_id = …` to "fix" a query hides
  whether the policy actually works. If a query returns too much, the policy is
  wrong — fix the policy.
- **`getUser()`, never `getSession()`.** `getSession()` returns whatever the
  cookie claims without validating it, and that value is fed straight into
  `request.jwt.claims`.
- **`SET LOCAL` inside a transaction, never a bare `SET`.** A plain `SET`
  persists on the pooled connection, so the next request inherits the previous
  caller's identity. No policy catches that.
- **`DATABASE_URL` must connect as a role without `BYPASSRLS`.** `postgres` and
  `service_role` both have it and would silently disable every tenancy policy
  while appearing to work.
- **`EventStore` has no `update` or `delete`.** The absence is the guarantee,
  and database triggers enforce it independently of the interface.
- **Sign-in failures return one generic message.** Distinguishing "no such
  account" from "wrong password" is a free account-enumeration oracle. The same
  applies to invitations: an unknown token and one addressed to somebody else
  give the identical error, or the endpoint becomes an oracle for who was
  invited.
- **No role has INSERT on organizations, users, projects, memberships or
  invitations.** See "The write path" below before adding one.

Tests that assert a policy must run as the `authenticated` role. Superusers
bypass RLS entirely, so asserting a policy while connected as one proves
nothing.

## Database changes

Migrations are the single source of schema truth, and every schema change ships
as a new numbered file in `supabase/migrations/`.

- Never hand-write DDL against the live database, and never edit a migration
  that has already been applied — add another one.
- Supabase project `zjsgpartbtbifxadzdsm` is the only project. Never provision a
  second one.
- Schema changes are not complete until a test exercises them against PGlite.

## The write path

Reads are governed by row level security. Writes to the onboarding tables are
not governed by policies at all, because no policy can express them: RLS says
"you see what you are a member of", and onboarding has to create the first rows
for somebody who is a member of nothing.

So those tables have **no INSERT privilege for any application role**. Every
write goes through a `SECURITY DEFINER` function in `supabase/migrations/0005`:
`bootstrap_organization`, `create_project`, `create_invitation`,
`accept_invitation`. They run as the owner and therefore bypass RLS, which makes
validating the caller their entire job — each one resolves the caller from the
verified JWT before anything else.

Two rules follow, and both matter:

1. **Do not grant INSERT on these tables** to fix a write that is refused. Add a
   function, or extend one, and test it. A test in `onboarding.test.ts` asserts
   that direct inserts are refused on every one of these tables; if it starts
   failing, the write path has been walked around rather than extended.
2. **Functions check structure; the domain checks capabilities.** These
   functions verify things like "the caller has no user row yet", "the caller's
   organization is this project's vendor side", "this invitation is unexpired
   and addressed to this confirmed address". They never evaluate a `Capability`.
   `authorize()` and `authorizeOrganization()` remain the only places the
   capability model lives, and they run in the server action first. Deliberately
   coarse in SQL, precise in the domain — the same split as the RLS policies.

Organization standing (`org_owner`/`org_admin`/`org_member`) is separate from
project roles and grants nothing inside a project. Being an owner of the
organization does not make you a member of its projects.

## Layers

`src/core` is pure domain: no React, no Next.js, no SDKs. ESLint enforces this —
if the boundary rule fires, the fix is to move the code, not to disable the rule.
`src/infra` holds adapters that satisfy `src/core/ports`. `src/app` is the only
place framework concerns belong.

## Frontend and brand

- The interface is **dark-only**. The identity is emissive artwork on true
  black; a light theme would lose it.
- The logo is **served as artwork and never redrawn** in CSS or type. Every
  asset in `public/brand/` is a lossless crop of the one original.
- Landing copy describes only what the domain actually supports. Do not promise
  capabilities the roadmap has not reached.

Full rules, including the edge-feather constraint, are in
`design/design-system.md`.

## Code style

Match the surrounding code. The distinguishing habit here is that comments
explain **why**, not what — they exist to stop a future reader "fixing"
something deliberate. If a line would look like a mistake to someone who wasn't
there, that is where a comment belongs. Everywhere else, prefer none.

## Before you commit

Run `pnpm verify` — typecheck, lint and tests, the same as CI. Commits use
conventional-commit subjects in lowercase, with a body that explains why rather
than what.

Do not add a dependency without asking first.
